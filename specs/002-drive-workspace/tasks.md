# Tasks: Workspace on Google Drive

**Input**: Design documents from `/specs/002-drive-workspace/`

**Prerequisites**: [plan.md](plan.md), [spec.md](spec.md), [research.md](research.md), [data-model.md](data-model.md), [contracts/drive-workspace.md](contracts/drive-workspace.md), [quickstart.md](quickstart.md)

**Tests**: required. Constitution V says every behavior change starts from an eval case that fails for the reason the change addresses. In each story phase, the eval cases come first, then a recorded red run, then the implementation.

**Docs**: constitution VII says a change updates every description of it in the same change. Each phase's pull request carries the docs for the behavior it changes. Phase 7 only reviews the docs.

**Organization**: tasks are grouped by user story, in the plan's delivery order: US4 + US5 → US1 → US2 → US3. v0.1.2 is cut only after two things: the release smoke test passes, connector checks included, and Fio has approved the constitution amendment.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: can run in parallel (different files, no dependency on an unfinished task)
- **[Story]**: the user story from spec.md

## Path Conventions

The repository root is the plugin source. The shipped plugin is `dist/vibebiz/`, built by `scripts/build_plugin.py`. Since spec 003 the source skills live in `src/skills/` and `scripts/build_plugin.py --skills` writes the tracked `.plugin-skills/` that every host manifest points at (`specs/003-multi-host/contracts/install-layout.md`); the `skills/` paths in the tasks below are those of their time and now read as `src/skills/`. `evals/` and `scripts/` never ship. Instruction files (`SKILL.md`, `core/`) are written with the `writing-for-agents` skill (CLAUDE.md). Vietnamese user text is edited with vietnamizer before its phase's pull request.

## Dependencies & Execution Order

### Phase dependencies

- **Setup (T001–T004)** comes first. T001 decides how every Drive eval case runs, and can stop the feature.
- **Foundational (T005–T007)** depends on T002 only for the shape of the fixtures.
- **US4 + US5 (T008–T018)** depends on Foundational. T017 gates only the tag (T048), not the stories.
- **US1 (T019–T032)** depends on US4 + US5, because §1 has to choose Drive mode before US1 can use it.
- **US2 (T033–T039) and US3 (T040–T046)** both depend on US1 and are independent of each other.
- **Release (T047–T050)** depends on every story. T049 and T050 come last; 0.1.2 was released without T049, which stays open (see T050).
- **Follow-ups (T057–T060)** belong to 0.1.3 (T060 stays open) and depend on nothing else in this spec.

### Within each story

The eval cases come first, followed by a recorded red run. Then the module, then the `SKILL.md` wording and docs, then the build and a green run.

### Parallel opportunities

- T003 and T004, after T002.
- T008–T011, which are separate case folders.
- T019–T025 and T051–T054.
- T031, beside T027–T030.
- US2 and US3, once US1 is done. They touch different files, except that both rebuild `dist/`, so run the builds one at a time.

Eval runs are heavy jobs. Run them one at a time, check `uptime` first, and keep each command to at most two modules.

## Implementation Strategy

### MVP

Setup, Foundational, US4 + US5 and US1 make the MVP. A web user can start an idea and keep it in Drive, and the desktop works as before. US2 makes it worth shipping, because ideas carry across devices. US3 completes the web flow.

### Incremental delivery

From Phase 3 on, each phase is one pull request. Each pull request gets code and security reviews, carries its docs, and records its red and green eval outcomes in `evals/RESULTS.md`. Version 0.1.2 is cut once, after Phase 7.
